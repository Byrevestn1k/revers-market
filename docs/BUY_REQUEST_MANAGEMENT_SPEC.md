# ТЗ: створення та повне керування запитом на покупку

## 1. Мета

Надати авторизованому користувачу-покупцю цілісний інтерфейс для:

- створення запиту на покупку;
- перегляду власних запитів і їхніх станів;
- повного редагування дозволених полів;
- скасування запиту;
- перегляду пропозицій продавців і переходу до вже наявного сценарію прийняття;
- відображення запитів на мапі за аналогією з товарами, без розкриття точної адреси.

## 2. Обов’язкові обмеження

1. Реалізація має використовувати наявну архітектуру React/Vite frontend, Express API та PostgreSQL/PostGIS.
2. Заборонено без попереднього дозволу власника:
   - змінювати бізнес-логіку запитів, пропозицій або замовлень;
   - змінювати структуру проєкту, архітектуру чи межі модулів;
   - змінювати наявні API-контракти, схему БД, статуси чи правила доступу;
   - видаляти, перейменовувати або переписувати наявний функціонал;
   - додавати нові залежності, зовнішні сервіси або міграції.
3. Якщо вимогу неможливо виконати без такої зміни, виконавець має зупинитися, описати причину, запропонувати мінімальні варіанти та отримати явний дозвіл.
4. Це ТЗ не надає дозволу на рефакторинг непов’язаних частин проєкту.

## 3. Наявні контракти, які потрібно зберегти

- `GET /api/categories` — категорії.
- `GET /api/buy-requests` — публічний список; `mine=true` — власні запити.
- `GET /api/buy-requests/:id` — деталі запиту.
- `POST /api/buy-requests` — створення.
- `PATCH /api/buy-requests/:id` — редагування та скасування.
- `GET /api/buy-requests/:id/offers` — пропозиції до власного запиту.
- `POST /api/offers/:id/accept` та `POST /api/offers/:id/reject` — наявний сценарій вибору пропозиції.
- `POST /api/offers/:id/conversation` — перехід до чату.
- `GET /api/map/markers` — маркери товарів і запитів.

## 4. Створення запиту

### 4.1. Доступ

- Створювати запит може лише авторизований користувач.
- Неавторизований користувач після натискання дії створення має побачити наявний сценарій входу/реєстрації, а після успіху — повернутися до форми.

### 4.2. Поля форми

| Поле | Вимога |
| --- | --- |
| Назва | Обов’язкова; чітко описує потребу. |
| Категорія | Обов’язковий вибір із наявного довідника. |
| Опис | Необов’язковий; вимоги до товару, якості та умов. |
| Кількість | Обов’язкове число, більше нуля. |
| Одиниця | Обов’язковий вибір із уже підтримуваних значень. |
| Мінімальна/максимальна ціна | Невід’ємні числа; мінімум не більший за максимум. |
| Валюта | Обов’язковий вибір із наявних валют. |
| Доставка | Наявні варіанти: не потрібна, потрібна, бажана. |
| Бажаний спосіб доставки | Використовує наявні значення API. |
| Кінцева дата | Необов’язкова; не може бути в минулому. |
| Регіон пошуку | Обов’язковий публічний текст. |
| Точна адреса | Необов’язкова; приватна, не виводиться у публічному DTO чи на мапі. |
| Координати | Обираються через мапу/геолокацію; ручне введення залишається доступним як наявна можливість. |

### 4.3. UX форми

- Поля мають мати зрозумілі назви, приклади та позначку обов’язковості.
- Помилка показується біля відповідного поля; загальна API-помилка — над кнопкою збереження.
- Під час надсилання кнопка блокується, повторне надсилання неможливе.
- Після успіху користувач потрапляє до деталей створеного запиту або до списку «Мої запити» з виділенням нового запиту.
- Повернення з форми до збереження не має знищувати введені дані без попередження.

## 5. Повне керування власними запитами

### 5.1. Список

Кожна картка запиту має відображати:

- назву, категорію та регіон;
- потрібну і вже закриту кількість;
- бюджет і валюту;
- вимогу до доставки;
- дедлайн;
- статус `open`, `partially_fulfilled`, `fulfilled`, `cancelled` або `expired`;
- кількість отриманих пропозицій, якщо це вже надається наявним API.

Потрібні стани інтерфейсу: завантаження, порожній список, помилка з повтором, заповнений список.

### 5.2. Деталі

Детальний перегляд має показувати всі дані, доступні власнику, прогрес виконання та дії, дозволені поточним статусом. Точну адресу не можна виводити у публічному режимі.

### 5.3. Редагування

- Форма редагування має використовувати ті самі компоненти, правила і валідацію, що й форма створення.
- Мають бути доступні всі поля, які дозволяє змінювати наявний backend.
- Після появи пропозицій заблоковані backend поля не мають виглядати доступними для редагування.
- При несумісному конфлікті або зміні стану на backend введені дані не втрачаються, а користувач отримує зрозуміле повідомлення.

### 5.4. Скасування

- Скасування вимагає явного підтвердження.
- Інтерфейс має пояснити, що скасування припинить приймання нових пропозицій.
- Після успіху статус оновлюється без перезавантаження сторінки.
- Фізичне видалення запиту не вимагається і не має додаватися без окремого погодження.
- Скасований запит не відкривається повторно. Якщо після скасування або після появи пропозицій потрібно змінити умови, власник створює новий запит на основі наявного: копіюються поля форми, але не статус, прогрес, пропозиції чи замовлення.

### 5.5. Пропозиції

- Власник бачить всі пропозиції до свого запиту, їхні статуси, продавця, товар, кількість, ціну, доставку та примітку.
- Наявні дії: відкрити чат, відхилити, прийняти повністю або частково.
- Кількість прийняття перевіряється відносно залишку пропозиції та запиту.
- Перед прийняттям показується підсумок: продавець, кількість, ціна за одиницю, загальна сума та умови доставки.
- Після успіху показується створене замовлення та оновлений прогрес запиту.

## 6. Відображення запитів на мапі

### 6.1. Загальна поведінка

- Використовується наявна мапа та `GET /api/map/markers`.
- Запити й товари мають різні, послідовні маркери та легенду.
- Користувач може окремо вмикати й вимикати маркери товарів і запитів.
- Фільтри категорії, геозони, радіуса та поточного центру мапи мають діяти на запити аналогічно до товарів.
- Переміщення або зміна масштабу оновлює результати без перезавантаження сторінки.

### 6.2. Приватність

- Маркер запиту показує лише наближену координату, яку вже повертає backend.
- Точна адреса, телефон та інші приватні дані не потрапляють до popup, картки, URL або клієнтських логів.
- Клієнт не обчислює публічну точку з точної адреси.

### 6.3. Маркер і картка запиту

Після вибору маркера відкривається картка з:

- назвою запиту;
- категорією;
- кількістю та одиницею;
- бюджетом, якщо він присутній у публічному DTO;
- регіоном та приблизною відстанню;
- дедлайном;
- кнопкою перегляду деталей.

Для власного запиту детальна картка додатково надає перехід до керування. Для чужого запиту зберігаються вже наявні правила перегляду та подання пропозиції.

## 7. Адаптивність і доступність

- Весь сценарій має працювати на мобільному екрані без горизонтального прокручування форм.
- Мапа, список результатів і деталі мають залишатися доступними на вузькому екрані.
- Усі кнопки і поля мають працювати з клавіатури та мати текстові підписи або `aria-label`.
- Помилки не позначаються лише кольором.
- Після закриття modal/popup фокус повертається до елемента, що його відкрив.

## 8. Обробка помилок

Інтерфейс має окремо обробляти:

- помилки валідації;
- втрату сесії;
- відсутність або недоступність запиту;
- конфлікт стану через нову пропозицію або прийняття;
- недоступність геолокації;
- мережеву або серверну помилку.

Повідомлення має бути зрозумілим для користувача і не розкривати stack trace, SQL або внутрішні дані.

## 9. Критерії приймання

1. Авторизований покупець може створити валідний запит з усіма полями з розділу 4.
2. Невалідні дані не надсилаються або відхиляються backend; UI показує польові помилки.
3. Створений запит одразу з’являється у «Моїх запитах» і на мапі за умови, що він має публічний статус і координати.
4. Власник може відкрити деталі та змінити всі дозволені backend поля.
5. Поля, заблоковані після отримання пропозицій, не можна змінити через UI.
6. Власник може скасувати дозволений запит лише після підтвердження.
7. Публічний маркер запиту не розкриває точну адресу.
8. Фільтри і перемикачі мапи коректно керують відображенням товарів і запитів.
9. З картки маркера можна відкрити повні публічні деталі, а для власного — перейти до керування.
10. Прийняття пропозиції підтримує повну і часткову кількість та оновлює прогрес запиту.
11. Стани loading, empty, error та success покриті для форми, списку, деталей, пропозицій і мапи.
12. Сценарій працює на desktop і mobile layout.

## 10. Перевірки

Мінімальний набір перевірок після реалізації:

- TypeScript typecheck для frontend і backend;
- наявні backend unit/integration tests;
- створення запиту з мінімальним і повним набором даних;
- валідація кожного обов’язкового поля і межових значень;
- повне редагування до та після отримання пропозиції;
- скасування та створення нового запиту на основі скасованого або такого, що вже має пропозиції;
- повне і часткове прийняття пропозиції;
- маркер запиту, пошук, фільтри, popup і перехід до деталей;
- перевірка, що публічні відповіді та мапа не містять точної адреси;
- ручна перевірка mobile layout та клавіатурної навігації.

## 11. Поза межами цього ТЗ

- зміна життєвого циклу пропозиції або замовлення;
- окрема адресна книга;
- оплата, escrow, логістика чи маршртизація;
- новий map provider або geocoding provider;
- нові ролі користувачів;
- переробка чату, замовлень, сповіщень, товарів чи профілів;
- рефакторинг або зміни, що не потрібні для виконання погодженого обсягу.
