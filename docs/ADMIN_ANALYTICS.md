# Admin analytics — Частина 1

Джерело — PostgreSQL, `GET /api/admin/dashboard`, permission `analytics.read`. Агрегація тільки backend, без окремого analytics сервісу. Фактична реалізація й визначення: `backend/src/admin/metrics.ts`.

## Часові межі й формули

`from <= created_at < to`, UTC, `from < to`, максимум 93 доби, майбутня верхня межа не більше 24 годин. Без параметрів — останні 30 днів до поточного часу. UI задає обидві дати на 00:00 UTC; дата «До» не входить у звіт. Усі запити одного звіту працюють у REPEATABLE READ read-only snapshot.

| Показник | Формула |
|---|---|
| Нові реєстрації | COUNT наявних `users` із created_at у періоді |
| Створені товари | COUNT наявних `products` у періоді, всі статуси |
| Створені запити | COUNT наявних `buy_requests` у періоді, всі статуси |
| Створені пропозиції | COUNT наявних `offers` у періоді, включно з чернетками |
| Створені угоди | COUNT наявних `orders` у періоді, всі джерела/статуси; кожна часткова угода окрема |
| Запити з відповіддю | 100 × кількість запитів cohort періоду з EXISTS нечернеткової Offer на момент звіту / кількість запитів cohort |
| Пропозиції з прийняттям | 100 × кількість нечернеткових Offer cohort періоду з accepted_quantity > 0 на момент звіту / кількість нечернеткових Offer cohort |
| DAU | NULL: достовірна історія активності відсутня |

Нульовий знаменник дає NULL — «Даних поки немає». Реальний COUNT=0 є достовірним нулем, а не демоданими. Щоденна серія групує created_at за UTC датою, містить дні з подіями; дні без подій не матеріалізуються. Вона не є вимірюванням відвідуваності.

Response/acceptance — **поточний стан cohort**, а не події прийняття в періоді й не історичний as-of звіт. Пропозиція після `to` може зробити старий запит answered; acceptance змінюється при звільненні резерву після скасування. Назви/описи метрик явно пояснюють поточну формулу. Один запит/Offer не множиться кількістю продавців чи часткових Deal. Completed quantity, виконання запиту, completed/cancelled Deal і distinct повторні угоди — ще не реалізовані.

Product status `sold` не створює метрику угоди. Поточний код містить справжні `orders.source=direct_product`, хоча частина старих product docs описує лише chat; рахується лише реальний order. Для наступної demand funnel потрібно відокремити `buy_request_id IS NOT NULL`, direct Product Deal — інший flow.

## Продуктивність і конфіденційність

- Timestamp range queries, індекси `(created_at DESC,id)` у міграції 066; correlated response/acceptance використовують існуючі зв’язки, без вибірки приватного контенту.
- Dashboard cache: до 32 конфігурацій на процес, TTL 60 секунд. Звіт показує generatedAt; свіжі зміни можуть з’явитися після TTL. Statement timeout 5 секунд.
- List API: максимум 100 рядків, page до 1000, q до 100 символів, стабільне сортування created_at/id, timeout 3 секунди. Пошук literal substring, без клієнтських SQL ідентифікаторів.
- Великий cohort усе ще потребує обробки всіх записів періоду; перевірка production-планів/обсягів попереду. Materialized rollups додавати тільки після вимірювання.
- Hard-deleted записи не відновлюються: ці дані не є повною історією marketplace. Відсутні історичні активні snapshots; не інтерпретувати стан зараз як стан на кінець минулого періоду.
- API не повертає приватні координати, адреси, контакти, повідомлення, фотографії чи довільні metadata. Географічної аналітики в цій частині немає.
- CSV/export endpoint відсутній, стандартний React-admin exporter вимкнено. Неавторизовані/непідтримувані запити відхиляються.

## Дані для наступних звітів

Наявні дані дозволяють розрахувати time-to-first-offer (mean/median для answered + unanswered окремо), accepted distinct Offers, підписки продавців, класифіковані скарги. Partial fulfillment треба спочатку групувати за request: completed `COALESCE(actual_quantity,quantity)`, не додавати різні одиниці; агрегувати нормалізовані частки запитів.

`users.last_seen_at` перезаписується й має історичний backfill, тому не є джерелом DAU/WAU/MAU/retention. Пошук/карта/перегляди/контакти/notification clicks і системні помилки не мають достатнього durable event collection. `PILOT_ANALYTICS.md` є контрактом, не доказом збору кожної події; поточні audit назви інші. Нових подій у цій частині не додано.

Новий звіт додається окремим визначенням, серверним query/service і компонентом; не збирати приватний текст/точні координати. Category/region фільтри, period comparisons, drilldown, CSV permission/ліміти, збережені конфігурації та geo suppression малих груп залишаються наступною частиною.
