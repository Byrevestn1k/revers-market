# Адміністративна панель — Частини 1–2

Гілка: `codex/admin-panel-analytics`, база `origin/main` = `242540866eedf36d1d9ac967666e4f9b31b691ec`.

## Реалізовано

- Окремий lazy-loaded React-admin модуль `/admin` з українським інтерфейсом, меню за permissions, входом через наявні cookie sessions і виходом.
- Серверний RBAC, незалежний від купівлі/продажу; строкові призначення, відкликання доступу, контрольоване offline створення Super Admin.
- Списки користувачів, товарів, запитів, пропозицій, угод, скарг та адміністративних подій: пагінація, пошук, мінімальні allowlisted поля. Це **перегляд**, не редактор комерційних даних; на телефоні використовуються компактні списки, на desktop — таблиці.
- Керування рольовими призначеннями іншому користувачу з підтвердженням, кодом причини та фактичним результатом backend.
- Dashboard: період UTC, справжні агрегати, ECharts лінії/стовпчики, loading/error/empty states. Формули й обмеження — [ADMIN_ANALYTICS.md](ADMIN_ANALYTICS.md).
- Безпека, матриця доступу та bootstrap — [ADMIN_RBAC.md](ADMIN_RBAC.md).

## Історичні межі Частини1

Це працездатна основа (Частина 1), а не завершення всього первісного ТЗ. Списки й початкові KPI додані для перевірки наскрізної роботи. Немає приховування/відновлення оголошень, platform ban, редактора модерації, нових правил спорів чи доступу до повідомлень/приватних фотографій.

В існуючому коді `MODERATOR_USER_IDS` окремо захищає старі moderation/dispute API. Він не надає автоматично RBAC, а нові ролі не надають автоматично legacy moderator доступ. Цю межу для reports закрито в Частині2; category/dispute policy лишається окремою. Особистий `user_blocks` не є блокуванням платформи. Не підміняти приховування зміною комерційного `status` без окремої policy і перевірок у всіх discovery/edit API.

## Частина2

Управління користувачами, незалежна moderation visibility, центр скарг, транзакційні рішення, безпечний локальний сценарій власника та цільова QA реалізовані. Повний опис і межі: [ADMIN_PANEL_PART2.md](ADMIN_PANEL_PART2.md). Перевірки: [qa/admin-panel/PART2.md](qa/admin-panel/PART2.md). Міграція067 застосовувалася лише до нової ізольованої admin_part2_test.

## Первісний план наступних контрольованих частин

1. **Управління (реалізовано Частиною2, межі оскаржень див. вище):** permission-based адаптери до чинних скарг/оскаржень; незалежний visibility state; серверне enforcement platform bans; транзакційний audit; фільтри статусу/категорії, картки й історія дій. Історичні умови Offer/Deal лишаються незмінними.
2. **Аналітика:** реєстр запитів із category/region фільтрами, попередній/довільний порівняльний період, перша пропозиція mean/median, distinct прийняття та quantity fulfillment, повторні угоди, безпечна географія, обмежений CSV з окремим permission, збережені конфігурації. Нові події — лише за визначеною потребою.
3. **Контекстні елементи:** окремий registry дій + permission-aware компактне меню для Product/Buy Request/Profile. Потрібні точки інтеграції: картка/деталі оголошення та профіль. На цьому етапі вони **не інтегровані**, щоб не торкатися компонентів Step 32. Backend authorization залишається обов’язковим для кожної дії.

Onboarding, FAQ, юридичні сторінки, Security & Geo Privacy не змінювалися. P1 geo search та Seller Offer photos цим етапом не виправлені; нові admin endpoints не повертають геометрію, фото, адреси чи приватний контент.

## Архітектура й залежності

`frontend/src/admin/`: auth/data providers, registry ресурсів, layout, Dashboard, Roles, i18n. `public-entry.tsx` зберігає чинну композицію звичайного сайту; main вибирає модуль за pathname. React-admin MIT, Apache ECharts Apache-2.0, MUI Material MIT, Emotion MIT; платних Enterprise API немає. Графіки підключають потрібні модулі ECharts.

`backend/src/admin/`: access middleware, router, resource registry, metrics, grants, bootstrap та тести. Міграція `066_admin_rbac.sql` створює role/permission/grant таблиці, початкову матрицю та індекси; вона не призначає жодному користувачу адміністративний доступ. Вхід захищено IP-лімітом на чинному password login endpoint; reverse proxy потребує окремого налаштування edge rate limit. Нові ролі/permissions можна додати міграцією без зміни назви бізнес-ролі користувача. Редактор визначень ролей/груп permissions ще не реалізований.

## Перевірки

Результати й точні сценарії: [qa/admin-panel/README.md](qa/admin-panel/README.md). Міграції застосовуються тільки до нового ізольованого контейнера/БД `admin_analytics_test` на localhost:55432. Основна БД не використовується. Push, merge, deployment не виконуються. Production потребує незалежного Sol Review, MFA, керування привілейованими сесіями й перевірки індексів на реалістичному обсязі.
