# Step 15 — розумний пошук

## Фактична поведінка

Product і Buy Request використовують одну функцію зіставлення у PostgreSQL. Пошук працює в каталогові Product, публічному API Buy Request і на карті `/discover` / `/map`. Слова запиту можуть бути в різних наявних полях: назва, опис, назва категорії та її батьківської категорії, одиниця виміру, публічний логін або псевдонім автора. За прямим рішенням користувача окремих полів для характеристик, бренду й моделі не додано. Якщо ці дані введені в назві або описі, пошук їх враховує. Приватні адреси й повідомлення не індексуються.

Запит обмежено 160 символами й 12 різними значущими токенами. Службові слова прибираються; цифри та буквено-цифрові моделі зберігаються. Порядок слів не впливає на базовий збіг. Для результату потрібно знайти щонайменше 60% значущих токенів; числові й буквено-цифрові токени мають збігатися обов’язково. Спершу відбираються кандидати, потім PostgreSQL обчислює релевантність: повнота запиту має найбільшу вагу, далі точний збіг, словоформа, префікс, обмежений нечіткий збіг і вага поля. Точна фраза в назві отримує бонус. За однакової релевантності порядок стабілізують дата й ID.

Українські та російські поширені закінчення нормалізуються контрольованою функцією. Окремі підтверджені відповідності охоплюють `детский`/`дитячий`, `яблоко`/`яблуко`, `самсунг`/`Samsung`. Це не повний переклад чи повноцінний морфологічний словник. Нечіткий пошук спирається на `pg_trgm`; короткі слова й токени з цифрами обробляються суворіше. Префікс слова має нижчий бал за точний збіг. Варіанти `12В`, `12 В`, `12v` нормалізуються для пошуку.

Міграція `047_smart_search.sql` додає `pg_trgm` і автоматично оновлюваний службовий `search_text`. Міграції `048_smart_search_candidates.sql` і `049_smart_search_short_circuit.sql` додають повні GIN-індекси Product і Buy Request, збережені словоформи та швидші функції перевірки збігу й оцінки. Старі оголошення залишаються в таблицях і отримують службові поля під час міграції. Фільтри категорії, місця, доставки й статусу застосовуються разом із текстовим запитом. Публічний список Buy Request має пагінацію; власні запити відсіюються на сервері до підрахунку сторінок. Пошук Buy Request також працює на карті.

## Виправлення швидкодії після review

Раніше PostgreSQL перевіряв і ранжував майже кожен рядок, бо складна умова з багатьох полів не давала використати GIN-індекс у головному запиті. Окремий `COUNT` повторював дорогу роботу. Тепер спершу відбираються кандидати через `pg_trgm` і спільні публічні поля категорії/автора. Остаточний збіг перевіряється збереженими словоформами; рейтинг обчислюється лише для відповідних рядків. Жорсткого ліміту кандидатів немає. `COUNT` використовує перевірку збігу без рейтингу. Перша й наступні сторінки повертають точний `total` через `count(*) OVER()`; запит окремого `COUNT` потрібен лише для порожньої сторінки за межами результатів. Порядок стабілізовано датою та ID. Фото Product завантажуються одним запитом на сторінку.

Публічні текстові запити до `/api/products`, `/api/buy-requests` і `/api/map/markers` обмежено 120 запитами за 60 секунд з однієї адреси. Після цього API повертає `429` і `Retry-After`. Адресу беруть із мережевого з'єднання, без довіри до довільного `X-Forwarded-For`. Пам'ять обмежено 10 000 адресами й очищенням прострочених записів. Ліміт локальний для одного процесу; для кількох backend-процесів потрібне спільне сховище лімітів і налаштований trusted proxy.

## Перевірка

- Unit, rate-limit і інтеграційні тести: `smart-search.test.ts`, `smart-search.integration.test.ts`, `search-rate-limit.test.ts`; повний прогін із локальною PostgreSQL: 237 пройшли, 1 пропущений. Перевірено Product, Buy Request, точні моделі й числа, кілька слів у різних полях, перестановку, помилки, префікси, фільтри, видимість, редагування, COUNT і сторінки.
- Вузький браузерний сценарій `e2e/step-15-correction.spec.ts`: 1440 і 390 px, 10 Product, сторінки 8+2 без повторів, категорія, область і карта — пройшов. Тестові записи прибрано за унікальною позначкою.
- Відтворювані виміри: `scripts/step15-benchmark.mjs` (тимчасова таблиця), `scripts/step15-api-benchmark.mjs` і `scripts/step15-request-benchmark.mjs` (по 10 000 позначених QA-записів із точковим прибиранням). Усі виміри: локальна PostgreSQL, прогрів, медіана трьох запусків, `EXPLAIN (ANALYZE, BUFFERS)` для SQL. HTTP вимірювався окремо. Набір навмисно широкий: одна категорія й один власник; це несприятливі умови для відбору кандидатів.

Порівняння на 10 000 синтетичних рядків (мс; попередній прогін мав одну вибірку, новий — медіану трьох, тому числа орієнтовні):

| SQL | Раніше: сторінка 1 | Зараз: COUNT | Зараз: сторінка 1 | Зараз: сторінка 2 |
| --- | ---: | ---: | ---: | ---: |
| 1 слово | 3699 | 370 | 1009 | 1275 |
| 3 слова | 3814 | 491 | 715 | 852 |
| 5 слів | 4042 | 1120 | 1103 | 926 |
| Помилка | 3944 | 784 | 1214 | 1090 |
| Географія | 3631 | 316 | 953 | 834 |
| Категорія + ціна | 991 | 418 | 789 | 525 |

Контрольний `EXPLAIN` показав `Bitmap Index Scan` на `step15_bench_trgm` для підрядкового й нечіткого пошуку (17 і 47 мс). Головний запит використовував цей GIN у однословному й нечіткому сценаріях; для широких 3/5 слів планувальник обрав послідовний перегляд. Порівняння старого та нового алгоритмів на тих самих 10 000 рядках дало 0 різних оцінок і 0 пропущених збігів для `червоний дитячий велосипед`, `велосепед`, `Samsung Galaxy S23`.

Повний Product API на 10 000 QA-записів (мс, медіана трьох; SQL виміряно окремо спрощеним SELECT):

| Запит | SQL COUNT | SQL стор. 1 / 2 | HTTP стор. 1 / 2 | Результатів |
| --- | ---: | ---: | ---: | ---: |
| `велосипед` | 557 | 1354 / 1187 | 1457 / 1393 | 10000 |

Для Buy Request на окремих 10 000 QA-записів: три слова — SQL COUNT 689 мс, сторінки 1009/863 мс, HTTP 1138/1070 мс; одне слово — HTTP 1237/1169 мс; помилка — HTTP 1567/1515 мс. GIN `products_search_text_idx` і `buy_requests_search_text_idx` використовуються у вибіркових і нечітких сценаріях. Час HTTP охоплює повний список полів, мережеву обробку й формування відповіді, тому не дорівнює часу спрощеного SQL SELECT.

## Межі

- Немає нових користувацьких полів характеристик, бренду й моделі згідно з рішенням користувача.
- Мовні відповідності обмежені явно закодованими правилами; довільні переклади й складні українські словоформи можуть не збігатися.
- Нечіткість допомагає дрібним помилкам, особливо після спільного початку слова; не всі перестановки чи помилки в перших літерах гарантовано знаходяться.
- Орієнтир близько 500 мс досягнуто для вибіркового запиту `Trek`, але не для широких запитів. Коли майже всі 10 000 оголошень мають ту саму категорію або одне слово, точний COUNT і оцінка багатьох допустимих кандидатів залишаються дорогими. Пропуски результатів або приблизний COUNT заради швидкості не вводилися. Перед великим навантаженням потрібне профілювання на реальному розподілі категорій і запитів.
