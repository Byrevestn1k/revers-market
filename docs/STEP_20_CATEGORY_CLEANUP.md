# STEP 20 — очищення категорій

## Що змінено

Міграція `053_category_taxonomy_cleanup.sql` залишає канонічний ID `apiculture` для продуктів бджільництва. У неї переходять зв'язки Product та Buy Request зі старих `honey`, `honey_raw`, `beeswax`, `pollen`, `propolis`, `royal_jelly`. `bee_packages` переходить до `bees`. Старі рядки й UUID залишаються в базі як неактивні; жодне оголошення не видаляється і не копіюється. `bees` і `queen_bees` перенесені до «Тваринництво». Повне дерево та рішення: [STEP_20_CATEGORY_AUDIT.md](STEP_20_CATEGORY_AUDIT.md).

Міграція `054_category_name_corrections.sql` перекладає польську назву «Pozostałe osobowe» та виправляє «Інші автозапчастин». Вона змінює лише назви й час оновлення двох категорій, не змінюючи їхні ID, батьківські вузли або підписки.

Міграція виконується стандартним runner у транзакції, а `schema_migrations` не дає їй запускатися повторно. Кожен `UPDATE` сам по собі повторюваний. Відновити старі зв'язки можна за таблицею кодів у міграції, але для точного повернення кожного Product/Request до початкового вузла потрібен знімок бази перед міграцією: після об'єднання цю інформацію не можна вивести з канонічного ID. Для production потрібні резервна копія й перевірка кількості рядків до застосування.

Локальна база перед міграцією: 1308 активних категорій, 6 Product і 7 Buy Request у `honey_raw`, 2 Product у `honey`, 1 активна підписка в `honey_raw`, жодної підписки на `apiculture`, `livestock` і `bees`. Користувач прямо обрав зупинити цю вузьку підписку; під час початкового локального запуску вона перенесена до канонічного ID з `active = false`. Її можна відредагувати й свідомо ввімкнути. Остаточний SQL **не змінює жодного рядка підписки**: він зупиниться за наявності активної або вимкненої підписки на `honey_raw`. Якщо перед переміщенням живих бджіл є підписки на `apiculture`, `livestock` або `bees`, він також зупиниться: їхнє охоплення зміниться через переміщення і об'єднання бджолопакетів. За наявності підписок на інші категорії, що виводяться з дерева, міграція теж зупиниться для окремого рішення. Так вона не розширює matching і не змінює чужі підписки мовчки.

Перед застосуванням 053 до іншої бази адміністратор має зробити резервну копію й зупинити запис у базу, потім виконати перевірку:

```sql
SELECT s.id, s.user_id, c.code, s.active, s.country_codes, s.regions,
       s.settlement_codes, s.min_quantity, s.max_quantity, s.unit,
       s.min_price, s.max_price, s.currency, s.receipt_methods, s.delivery_options
FROM demand_subscriptions s JOIN categories c ON c.id = s.category_id
WHERE c.code IN ('honey_raw', 'honey', 'beeswax', 'pollen', 'propolis', 'royal_jelly', 'bee_packages', 'apiculture', 'livestock', 'bees');
```

Якщо SELECT знаходить підписки, міграцію не застосовувати до окремого погодження конкретного способу збереження їхнього змісту для цієї бази. Самого вимкнення підписки недостатньо: її майбутнє охоплення також потребує рішення. За відсутності таких підписок запустити `npm run db:migrate`; у разі помилки транзакція 053 відкочується. Перед відновленням запису перезапустити API, щоб очистити наявний хвилинний кеш рекомендацій категорій. Лише після успішної перевірки відновити запис у базу.

`category-filter.ts` зіставляє старі ID фільтрів із активним батьком. `/api/categories` повертає активне дерево та `legacyIds` канонічних вузлів, щоб збережений у браузері старий фільтр карти автоматично показав правильну категорію. API створення оголошень і нових підписок і далі приймає лише активні ID. Форми беруть один список через `/api/categories`; приховані вузли не повертаються після оновлення сторінки. Smart Category рекомендації меду, пилку, перги, прополісу, бджолиного воску та маточного молочка ведуть до `apiculture`, а інструменти пасіки — до наявної категорії обладнання. Семантичне блокування HTTP 422 не вмикалося. Deal snapshots, Favorites, Offers, старі скарги й географічні дані міграція не змінює.

## Перевірка та ризики

- Пробний запуск міграції на локальній базі зроблено всередині транзакції з `ROLLBACK`: очікувалися 8 Product і 7 Buy Request у `apiculture`, 1 вимкнена підписка, 0 активних старих вузлів. Потім застосовано до локальної тестової бази через `npm run db:migrate`.
- Історичні Deal snapshots лишаються без змін, бо SQL торкається тільки категорій, Product, Buy Request і однієї групи підписок.
- Текстовий пошук «мед» після зміни категорії залежить від тексту оголошення; усі 8 локальних товарів і 7 запитів зі старих медових категорій мають «мед» у назві. Для інших баз це потрібно перевірити окремо.
- Початковий локальний SQL перевірено на відтвореній старій структурі в транзакції з `ROLLBACK`: Product і Buy Request перейшли до `apiculture`, погоджена вимкнена підписка збереглася, решта полів оголошень, знімки `order_items` і кількість сповіщень не змінилися. Остаточний SQL суворіший: автоматичний replay перевіряє, що активні й вимкнені підписки на мед і будь-які підписки на `apiculture`, `livestock`, `bees` зупиняють міграцію до окремого рішення; без таких підписок перенесення оголошень та повторний запуск проходять у транзакції з відкатом.
- `npm run typecheck` — PASS. Повний послідовний `npm test --workspace backend` із локальною PostgreSQL — **254 PASS, 1 SKIPPED**, 45 тестових файлів PASS; пропущено спеціальний `demand-suburbs.live.integration.test.ts`. У попередніх запусках під навантаженням траплялися таймаути; фінальний прогін на остаточному коді завершився з кодом 0. Окремий повтор рекомендацій і тест захисту підписок також пройшли.
- Chromium: створено й відредаговано QA Product і Buy Request, змінено категорію на «Фрукти» та повернуто «Продукти бджільництва». Окремо створено QA Product, Buy Request і вимкнену підписку зі старим ID, перенесено міграцією 053 і перевірено: обидва редактори показують канонічну категорію та зберігають зміни (HTTP 200), підписка відображається вимкненою й доступна для редагування. Усі ці QA записи прибрано після перевірки. Перевірено старі прямі посилання, старий ID у фільтрі й відновлення збереженого фільтра, пошук «мед», відкриття групи карти, підсвічування маркера при виборі картки, рекомендацію для прополісу та вибір категорії для нової підписки. Форми Product, Buy Request, підписки й карта перевірені на 1440, 1280, 1024, 768, 390 і 320 px без горизонтального переповнення. На 320 px перевірено перехід між рівнями та кнопку «Назад». На вузьких екранах назва вибраної категорії тепер додатково показується повністю. Обидві виправлені назви знайдено й вибрано на 320 px. Скріншоти: `docs/step20-browser-qa/`.
- На карті при 320 px деякі географічні групи накладаються одна на одну. Порівняння з frontend `main` на тих самих поточних даних відтворило проблему в обох версіях; її винесено в [окремий backlog](BACKLOG_MAP_GROUP_OVERLAP.md). Алгоритм Step 18 у цій роботі не змінювався. Відкриття доступної групи та її карток перевірено на 1440 px.
- Фізичний Android — UNVERIFIED. Показ саме вимкненої підписки її власнику в браузері — UNVERIFIED; її стан перевірено в локальній базі. Точна зворотна міграція окремих оголошень потребує резервної копії до 053.
- Попередній незалежний Sol надав **REVIEW PASS**; після додаткового посилення SQL-захисту підписок остаточний коміт потребує повторного незалежного перегляду. Рев'юер не мав доступу до локальної PostgreSQL; результати запусків БД наведено вище за перевірками виконавця.

## Статус

**NOT READY для інтеграції:** перегляд саме підписки фактичного власника та спеціальний live-тест передмість залишаються UNVERIFIED. Відтворене також у `main` накладання груп на 320 px ведеться окремо в backlog. Перед застосуванням до іншої бази треба виконати описаний preflight підписок і перевірити пошук оголошень, у тексті яких немає назви колишньої категорії. Merge і push потребують окремого дозволу користувача.
