# Step 25 — центр сповіщень: робота триває

## Аудит

| Наявна можливість | Стан до Step 25 | Допрацювання |
| --- | --- | --- |
| Таблиця notifications | Є контекст, час прочитання та посилання на запит, чат і угоду | Історія з курсором та окремий перегляд записів без контексту |
| Підписки продавця | Критерії та захист від дублювання subscription/request уже існують | Посилання на наявні налаштування |
| Події пропозицій, угод і чатів | Створюються наявною бізнес-логікою | Перевірка переходів і представлення |
| Центр і мобільний індикатор | Уже існують | Фільтр, вкладки та дзвіночок у шапці |

Нові події з контекстом buying і selling відображаються у відповідних вкладках. Старі події без контексту зберігаються окремо у вкладці «Інші події»: роль неможливо достовірно визначити. Загальний лічильник включає їх один раз. Масове прочитання діє лише на вибрану вкладку. Відкриття центру не позначає події прочитаними.

## API

`GET /api/notifications` підтримує `context=buying|selling|legacy`, `unread=true|false`, `limit` від 1 до 100 та непрозорий `cursor`. Відповідь містить `notifications`, `nextCursor` і `unreadCounts` з `total`, `buying`, `selling`, `legacy`. Порядок — час створення та ID за спаданням. `PATCH /api/notifications/read` приймає `notificationId` або `context` та обмежує оновлення власником. Існуючий виклик без параметрів зберігається для сумісності.

Підписки налаштовуються на наявній сторінці `/settings/demand-subscriptions`. Алгоритми matching та захист від дублювання не змінювалися.

- Browser QA у Codex Local: Chromium, реальний API й окрема PostgreSQL `step25_test` на порту 55432. На 390, 1280, 1440, 1024, 768 і 320 px пройдено вхід через UI, вкладки, лічильники, фільтр, завантаження наступної сторінки, прочитання одного й усіх подій вибраної вкладки, збереження непрочитаного в інших вкладках і перехід до налаштувань. Перевірено горизонтальне переповнення і положення кнопок. [Скриншоти](evidence/step-25/). Дані подій підготовлені безпосередньо в тестовій БД.
- Фізичний Android: **UNVERIFIED**.
- На 390 і 1280 px перевірено перехід покупця до нової пропозиції та продавця до відхиленої пропозиції з фокусуванням відповідної картки. Запит, пропозицію і відхилення створено через реальний API. Повний життєвий цикл створення через UI, переходи до чату й угоди та фізичний Android залишаються неперевіреними.
- Оновлена регресія з підставними відповідями API: 6/6 PASS, включно з довгими текстами на 320, 390, 768, 1024 і 1440 px та відновленням після помилки прочитання. Реальні сценарії центру: 6/6 PASS; переходи до пропозицій: 2/2 PASS.
- `npm run typecheck`: PASS. Повний набір на окремій PostgreSQL: 266 passed, 6 skipped, один набір не пройшов через тайм-аут підготовки 10 секунд під навантаженням. Окремий повтор цього набору з більшим тайм-аутом: 5/5 PASS; один live-тест залишається пропущеним за умовою. Міграція 055 перевірена лише на окремій тестовій базі, не на основній.
- Sol виконав попередній статичний перегляд і після виправлень не виявив нових конкретних помилок у перевірених міграції, доступі та переходах. Остаточний REVIEW PASS відсутній; цю гілку підготовлено для незалежного повторного перегляду.


Для нових подій створення, оновлення, відкликання та відхилення пропозиції API повертає `offerId`. Події переговорів ведуть до чату через `conversationId`. Покупець переходить до конкретної пропозиції у своєму запиті, продавець — до власної пропозиції. У старих подій без `offerId` зберігається перехід до пов’язаного чату, запиту або угоди. Міграція `055_notification_offer_reference.sql` додає необов’язкове поле, а видалення пропозиції очищає посилання без видалення сповіщення.
