# Правила commit і push

Ці правила допомагають швидко відокремити результат роботи від локальних даних. Вони не замінюють перевірку `git diff`, але дозволяють не переглядати щоразу runtime-файли та особисті дані.

## Додавати до commit

Додавайте лише файли, які є частиною відтворюваного результату роботи:

- код у `frontend/src/` і `backend/src/`;
- migrations у `backend/db/migrations/`;
- automated tests, Playwright сценарії та їх конфігурацію;
- зміни `package.json` і `package-lock.json`, якщо для задачі справді додано або оновлено залежність;
- документацію в `docs/`, якщо вона описує актуальний продукт, QA, setup або рішення;
- кореневі конфігураційні файли, потрібні всім розробникам, наприклад `.gitignore` чи `playwright.config.ts`;
- навмисно додані матеріали в `ТЗ/` лише коли користувач прямо попросив зберегти їх у репозиторії.

## Не додавати до commit або push

Не додавайте локальні, секретні або відтворювані файли:

- `.env`, ключі, токени, паролі та `docs/TEST_ACCOUNTS.local.md`;
- `node_modules/`, `dist/`, `.vite/`, coverage, логи та TypeScript build info;
- `playwright-report/` і `test-results/`;
- `backend/uploads/`: це файли, які завантажили користувачі або створили QA-тести, а не source code;
- тимчасові Office lock-файли на кшталт `ТЗ/~$*.docx`;
- випадкові локальні файли, screenshots або exports, якщо їх окремо не попросили додати.

Якщо незрозуміло, чи потрібний untracked файл, не додавайте його автоматично. Спочатку визначте, чи без нього інший розробник зможе відтворити функцію, тест або документацію.

## Короткий робочий порядок

1. Подивіться тільки короткий список: `git status --short`.
2. Додайте явним списком лише файли поточної задачі: `git add -- <файли>`.
3. Перевірте staged зміни: `git diff --cached --stat` і `git diff --cached --check`.
4. Створіть один commit з коротким описом завершеного результату.
5. Перед push перевірте `git status --short --branch`, потім виконайте `git push origin <гілка>`.

Не треба вручну перебирати ігноровані файли: вони не з'являтимуться у звичайному `git status`. Не використовуйте `git add -A`, якщо у робочій теці є невідомі неігноровані файли; явний список краще захищає від випадкового commit.

## Коли робити окремий commit

Робіть окремий commit, коли зміна є самостійною і її можна перевірити окремо: наприклад, функція з тестом, документація, або виправлення UI з Browser QA. Не змішуйте випадкові форматування, runtime uploads і чужі незавершені зміни з результатом поточної задачі.

## Перед push

Push дозволений після того, як commit створений, перевірка пропорційна ризику виконана, а staged diff не містить секретів чи локальних артефактів. Якщо commit змінює production behavior, у повідомленні або PR треба коротко вказати, що змінилося і які перевірки були запущені.

## Фіналізація вже перевіреної задачі

Якщо задача вже має явний статус `DONE`, `PASS`, `APPROVED FOR MERGE` або інший еквівалентний висновок Reviewer, commit/merge/push вважається окремою технічною фазою фіналізації.

У цій фазі не потрібно повторювати вже виконану перевірку задачі.

Не виконувати без конкретної причини:

- повторний code review;
- повторне читання `AGENTS.md`, `docs/`, `PROJECT_STATE.md`, `PRODUCT.md`, `README.md` та іншої документації;
- повторний запуск `npm test`, Playwright, Browser QA, typecheck, build або lint;
- перегляд повного `git diff`, якщо список файлів поточної задачі вже відомий;
- дослідження `git log`, `git branch`, `git remote` або історії репозиторію, якщо поточні branch і target branch вже відомі;
- повторення однакових Git-команд без нової причини;
- аналіз сторонніх локальних змін або stash, якщо вони лише безпечно зберігаються і не повинні входити в поточну задачу.

### Мінімальний порядок фіналізації

Для вже перевіреної задачі використовувати мінімально необхідну послідовність:

1. `git status --short`
2. Додати явним списком лише файли поточної задачі:
   `git add -- <файли>`
3. `git diff --cached --stat`
4. `git diff --cached --check`
5. `git commit -m "<короткий опис результату>"`
6. Якщо commit створювався в окремій гілці або worktree — інтегрувати його в цільову гілку.
7. `git status --short --branch`
8. `git push origin <гілка>`
9. `git status --short`

Не використовувати `git add -A`, якщо у worktree є невідомі або сторонні неігноровані файли.

### Merge вже перевіреного commit

Якщо source commit уже пройшов Reviewer і merge:

- виконаний fast-forward; або
- пройшов чисто без конфліктів і без ручного редагування коду,

сам факт merge не є причиною повторно запускати повний test suite, build, typecheck або інший повний QA.

Після такого merge достатньо короткої Git-перевірки:

- `git status --short --branch`
- `git diff --check`

Повторна повна validation потрібна лише якщо:

- merge мав конфлікти і вони вирішувалися вручну;
- після Reviewer змінювався функціональний код;
- під час merge або commit виникла помилка, яка може впливати на результат;
- інтеграція змінила поведінку коду понад уже схвалений commit;
- користувач прямо попросив повторну перевірку.

### Робота зі stash

Якщо локальні зміни треба лише тимчасово захистити перед commit або merge:

1. перевірити `git status --short`;
2. створити named stash, за потреби разом з untracked files:
   `git stash push -u -m "<опис>"`
3. переконатися, що stash створений;
4. продовжити Git-фіналізацію.

Без окремої вказівки не виконувати:

- `git stash pop`;
- `git stash apply`;
- `git stash drop`.

Не аналізувати і не порівнювати вміст stash з новим `main`, якщо поточна задача полягає лише в безпечному збереженні локальних змін.

### Коли зупинитися

Зупинити автоматичну фіналізацію і повідомити проблему, якщо:

- виявлені невідомі або сторонні зміни, які можуть випадково потрапити в commit;
- незрозуміло, які файли належать поточній задачі;
- `git diff --cached --check` або `git diff --check` показує проблему;
- commit не створюється;
- checkout або merge заблокований;
- виник merge conflict;
- push відхилено;
- незрозуміло, яка гілка є цільовою.

Не починати широкий аудит репозиторію автоматично. Спочатку повідомити конкретну Git-проблему.

## Принцип мінімальних Git-операцій

Git-фіналізація вже перевіреної задачі не повинна перетворюватися на повторний аудит проєкту.

Якщо команда не потрібна для:

- безпечного staging;
- commit;
- merge;
- push;
- збереження локальних змін;
- або діагностики конкретної Git-помилки,

її не виконувати.

Віддавати перевагу коротким Git-виводам (`--short`, `--stat`) замість великих diff/log output, якщо детальний вивід не потрібний для прийняття рішення.

## Короткий фінальний звіт

Після успішної фіналізації достатньо вказати:

- commit hash;
- branch;
- merge method, якщо був merge;
- push: `OK` / `FAILED` / `NOT PERFORMED`;
- working tree: `CLEAN` / `DIRTY`;
- stash reference, якщо stash використовувався.

Не створювати великий звіт, якщо під час Git-фіналізації не виникло проблем.
