# UX/UI контракт marketplace-navpaky

Це постійний контракт для майбутньої роботи. Він не описує автоматично правильний поточний UI: розбіжність із ним є UX gap, а не приводом послаблювати правила.

## Загальні принципи

Інтерфейс призначений для звичайного користувача. Основна дія сторінки має бути очевидною, другорядні дії не перевантажують екран, а однакові сутності й дії виглядають та називаються послідовно. Не ховати критично важливу інформацію без потреби; не показувати внутрішні API-статуси як основний текст. Статуси мають бути зрозумілою українською.

## Responsive

Desktop, tablet і mobile мають бути повноцінними режимами; горизонтальний overflow сторінки неприпустимий. На вузькому екрані можна змінювати порядок, переносити metadata, приховувати другорядне, перетворювати дві панелі на послідовні екрани та переносити другорядні дії в меню. Не обрізати першими назву, ціну, кількість, ключовий статус або основну дію.

## Навігація

Користувач завжди розуміє поточний екран, відкритий об’єкт, шлях повернення та наступну основну дію. Вкладені mobile-екрани мають очевидне «Назад». `×` закриває modal/dialog і не є основною кнопкою повернення між логічними екранами.

### Canonical URLs

Навігаційний стан основних екранів зберігається у path, а не лише у React-state. Поточний canonical contract:

| Destination | Route |
| --- | --- |
| Кабінет / пошук / каталог / мапа | `/dashboard`, `/discover`, `/products`, `/map` |
| Власні товари / новий товар | `/my/products`, `/my/products/new` |
| Discovery запитів / власні запити / новий запит | `/requests`, `/my/requests`, `/my/requests/new` |
| Угоди / сповіщення / налаштування профілю | `/orders`, `/notifications`, `/settings/profile` |
| Товар / запит / публічний профіль | `/products/:id`, `/buy-requests/:id`, `/profiles/:username` |
| Повідомлення / конкретна розмова | `/messages`, `/messages/:conversationId` |

Старі внутрішні `?view=...` links нормалізуються до canonical path. Detail view відновлює дані через чинний API після прямого відкриття або refresh. Breadcrumbs розміщуються в main content, parent є справжнім посиланням, а current item не є посиланням на себе. На mobile розмова зберігає list-first → active conversation flow і логічне повернення до `/messages`.

## Product і Buy Request

Це різні сутності, але картки мають споріднену структуру й чіткий маркер типу.

- **Product:** фото/fallback категорії → назва → ціна → кількість/одиниця → продавець → місце/відстань → доставка → релевантний статус.
- **Buy Request:** маркер «Шукає» → назва → потрібна кількість → бюджет за наявності → покупець → місце/радіус → строк → доставка.

Картка не замінює повну сторінку об’єкта.

## Offer

Offer — конкретна пропозиція продавця покупцеві, не ще одне оголошення. Пріоритет: продавець і репутація за наявності, товар/варіант, кількість, ціна за одиницю, однозначно обчислена сума, доставка, доступність, умови й статус. Основні дії покупця мають бути відокремлені від другорядних. Переговори відбуваються у пов’язаному чаті без ручного створення нової сутності.

## Чати

За достатньої ширини показувати `[ список чатів ][ активний чат ]`. На mobile показувати або список, або активний чат; відкриття веде до діалогу, а `← Назад` — до списку. Не ставити довгий список над активним діалогом.

У списку пріоритет: контекст товару/запиту/пропозиції, співрозмовник, комерційна інформація, останнє повідомлення, unread, час. Розрізняти direct, offer і deal chat, але не змушувати користувача розуміти внутрішні терміни. У чаті має бути зрозуміло, з ким розмова, про що вона, актуальні умови/стан та наступна дія.

## Deal і часткове виконання

У UI вживати зрозумілий термін «Угода» або «Замовлення», не показувати state machine без потреби. Показувати учасника, предмет, кількість, погоджену ціну і суму, доставку/отримання, стан і сторону наступної дії. Не показувати кілька взаємовиключних primary actions без пояснення.

Небезпечні дії (відмова, скасування, завершення, невдала угода) потребують підтвердження з поясненням наслідку. Для часткового request чітко розділяти: потрібно загалом, вибрано/зарезервовано, завершено та залишилось; при прийнятті показувати конкретну кількість і не створювати враження повного виконання.

## Карта

Карта — ключовий інструмент: місце/продавець/покупець → релевантні оголошення → конкретний Product або Buy Request. Маркер, коротка й повна картка мають послідовну ієрархію. Вибір маркера не відкриває повний об’єкт несподівано. На mobile має бути зрозумілий зв’язок карти, точки, короткої картки й результатів. Не розкривати приватну точну адресу без дозволу або прав учасника.

## Форми, стани й feedback

Форми групують пов’язані поля, мають labels, одиниці, пояснення складних полів і validation біля проблемного поля; за можливості зберігають введене після помилки. Не запитувати зайвого, primary submit має бути очевидним.

Для важливих асинхронних екранів передбачати: **LOADING** (дані завантажуються), **EMPTY** (чому порожньо і наступний крок), **ERROR** (зрозуміле повідомлення та повторна спроба за потреби). Після важливої дії показувати успіх, помилку, очікування іншої сторони або зміну стану.

## Confirmation, accessibility і consistency

Destructive actions мають відрізнятися від primary actions. Підтвердження потрібне для скасування угоди, видалення, істотної відмови, публікації приватних даних і незворотного завершення; воно пояснює наслідок, а не лише питає «Ви впевнені?».

Mobile targets мають бути достатніми. Не покладатися лише на колір, не створювати неоднозначних вкладених clickable зон, не ламати keyboard focus у modal/dialog. Повторно використовувати придатні кнопки, badges, cards, dialogs, inputs і status indicators; не вводити новий pattern без потреби.

## Правило для AI-агентів

1. Прочитати релевантний розділ цього документа та перевірити поточний UI.
2. Не змінювати business logic заради UX без окремої потреби.
3. Зробити мінімальну узгоджену зміну та провести Browser QA за `AGENTS.md`.
4. Для responsive-змін перевірити desktop, tablet і mobile.
5. UX-проблеми поза scope повідомляти, а не виправляти прихованим redesign.

Якщо UX_RULES суперечить бізнес-логіці, спочатку звірити `PRODUCT.md`, код, migrations і tests та повідомити про конфлікт.
